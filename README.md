# project-implementation-RD

Repository for the research and development work on the 247-519-VA (Project I) project at Vanier College: an ESP32-based smartwatch and custom waist-worn system for fall detection and caregiver alerting.

## Contents

### `documents/proposal/`
The written Project Proposal, built in LaTeX.

- `proposal.tex` main document; pulls in the table files below via `\input`.
- `table1_stakeholder_needs.tex` to `table5_uncertainties.tex` the proposal's tables.
- `Proposal.pdf` compiled output.

### `documents/gate1/`
The Stage 1 Concept and Feasibility Report (Gate 1), built in LaTeX.

- `gate1_report.tex` main document; pulls in the table files below via `\input`.
- `table1_change_log.tex` to `table7_top_risks.tex` the report's tables.
- `gate1_report.pdf` compiled output.

### `figures/generated/`
- `context_diagram.pdf` system context diagram, generated by `src/context_diagram.py`.
- `watch_functional_block_diagram.png` watch functional block diagram.
- `concept_a_block_diagram.png` functional block diagram of concept A, cropped from the watch diagram.

### `src/`
- `context_diagram.py` regenerates the context diagram.
- `watch_WiFi_OLED_test/` Wi-Fi and display bring-up sketch for the watch.
- `watch_MQTT_test/` MQTT connection test for the watch: publishes a test alert to the broker on each BOOT press (copy `secrets_example.h` to `secrets.h` first).
- `FallDetector_trials/` watch firmware: IMU sampling at 238 Hz, impact-triggered fall classifier, 15 s cancel window, MQTT alerts, 60 s post-fall check, on-screen status, and SD logging with button-marked test trials.
- `dashboard/` Raspberry Pi alert screen (`screen.py`) and a laptop test publisher (`publisher.py`).
- `waist_sensor_test/` checks the waist board on a breadboard: ESP32 with an MPU6050 (accel/gyro) and a BMP280 (pressure) on I2C.
- `WaistBoard/` waist board firmware: samples at 238 Hz and sends its features to the watch over Bluetooth LE for the fused model.
- `fall_model/` training pipeline for the wrist and fused classifiers (FallAllD to features to random forest to C header) and C-versus-Python parity checks.
- `session_analysis/` tools that clean and score the SD card logs from watch test sessions, the post-fall check trials and the alert delivery tests.

### `data/`
- `features/` outputs of the training pipeline (`features.csv`, `wrist_windows.csv`, feature order, Python reference windows for the parity check).
- `sessions/` watch test logs, original and cleaned, plus the raw IMU recordings; `sessions/postfall/` and `sessions/link/` hold the post-fall and delivery tests.
- `fallalld/` instructions for recreating the FallAllD subset (the data itself is not committed). The dataset is on [IEEE DataPort](https://ieee-dataport.org/open-access/fallalld-comprehensive-dataset-human-falls-and-activities-daily-living).

## Reproducing the wrist fall model

Requires Python 3 with the packages in `requirements.txt` (tested with Python 3.13, numpy 2.5, pandas 3.0, scipy 1.18, scikit-learn 1.9) and gcc for the parity check. Run from the repository root; the scripts locate files relative to themselves.

1. Create the FallAllD subset as described in `data/fallalld/README.md` (`data/fallalld/my_subset_v2`).
2. `python src/fall_model/build_features.py` whole-trial features and the subject split to `data/features/features.csv`.
3. `python src/fall_model/baseline.py` optional whole-trial baseline.
4. `python src/fall_model/wrist_windows.py` impact windows and the 14 features to `data/features/wrist_windows.csv`.
5. `python src/fall_model/wrist_classify.py` cross-validated threshold and test-subject evaluation.
6. Set `THR` in `src/fall_model/export_c.py` to the threshold printed in step 5, then `python src/fall_model/export_c.py` to train the deployed model and write `src/FallDetector_trials/fall_model.h`.
7. `python src/fall_model/parity_test/parity_check.py` checks that the C detector matches the Python model.

## Reproducing the fused wrist + waist model

1. Create `data/fallalld/my_subset_fusion` as described in `data/fallalld/README.md`.
2. `python src/fall_model/fusion_windows.py` impact windows with wrist features, waist features and the height change.
3. `python src/fall_model/fusion_classify.py` compares wrist-only, waist-only and fused models on the same trials.
4. `python src/fall_model/fusion_export_c.py` picks the threshold, trains the fused model and writes `src/FallDetector_trials/fall_model_fusion.h`.
5. `python src/fall_model/fusion_parity.py` checks that the C code matches Python and that the waist board's feature code is identical to the watch's.

Model summary (v2): wrist logger, 2,515 trials from 13 subjects, all 79 activities. Trigger at 2.5 g, window of 1 s before and 2 s after the peak, 14 features, random forest of 100 trees (depth 6), decision threshold 0.30. Subjects are split by number: validation 7, 10, 13; test 2, 9, 14. The first model (v1) used 1,541 trials, 45 activities and threshold 0.26.

## Watch test sessions

`python src/session_analysis/clean_sessions.py` writes the clean logs; `python src/session_analysis/analyze_session.py` scores them. Details are in `data/sessions/README.md`.

| Session | Model | Trials | Result |
| --- | --- | --- | --- |
| Round 1, real falls | v1 | 20 | 19 detected, 1 missed |
| Round 1, non-falls | v1 | 10 | 8 false alarms |
| Round 2, real falls | v2 | 20 | 20 detected |
| Round 2, non-falls | v2 | 20 | 11 false alarms |
| Round 3, real falls | fused wrist + waist | 20 | 20 detected |
| Round 3, non-falls | fused wrist + waist | 20 | 11 false alarms; the wrist model alone would have raised 18 |

The false-alarm rate is far above the under-10% target in every round. In round 3 the waist board removed 7 of the 18 false alarms the wrist model would have raised on the same movements; the ones left were sitting down hard, hard arm swings and the wrist hitting a table or the body. The non-fall movements in round 3 were harsher than in round 2, so the two rounds' false-alarm counts are not directly comparable. The sample sizes are too small to show that the miss-rate target is met.

## Alert path

Watch → MQTT over Wi-Fi → Mosquitto broker on the laptop → Raspberry Pi, which subscribes to `pi/dashboard/#` and shows the alert.

1. Broker: in `mosquitto.conf` set `listener 1883` and `allow_anonymous true`, then run `mosquitto -c mosquitto.conf -v`. Allow inbound TCP 1883 in the laptop firewall.
2. Watch: copy `src/FallDetector_trials/secrets_example.h` to `secrets.h` in the same folder and fill in the Wi-Fi name, password and the laptop's IPv4 address. `secrets.h` is not committed. Build settings are at the top of the sketch.
3. Pi: set `BROKER` in `src/dashboard/screen.py` to the laptop's address, then `pip install paho-mqtt` and `python3 screen.py`.

After a detected fall the watch waits 15 s for a BOOT cancel, then publishes the alert. It then watches for wrist movement: 60 s in a row with none publishes an escalation. A BOOT press after the alert is sent tells the dashboard the wearer is OK. The Pi acknowledges every message, and the watch resends until it does. Message formats are in `src/FallDetector_trials/README.md`; the Pi logs every alert to `alerts_log.csv` with its delay since detection.

### Alert delivery (REQ-FD-02)

`python src/session_analysis/link_results.py` rebuilds the results in `data/sessions/link/`. Delay is from detection on the watch to arrival at the Pi, and includes the 15 s cancel window.

| Run | Firmware | RSSI (dBm) | Fall alerts delivered | Fall alert delay (s) | Watch restarts |
| --- | --- | --- | --- | --- | --- |
| Strong link | no ack | -53 to -71 | 10 of 10 | 15.22-15.38 | 0 |
| Weak link | no ack | -65 to -78 | 9 of 10 | 15.06-15.53 | 1 |
| Weak link | ack | -71 to -79 | 10 of 10 | 15.07-24.48 | 1 (watchdog) |
| Moderate link | ack, watchdog fix | -66 to -74 | 10 of 10 | 15.01-15.08 | 0 |
| Broker stopped 10-15 s | ack, watchdog fix | -63 to -65 | 5 of 5 | 28.29-40.10 | 0 |
| Broker suspended about 20 s | ack, watchdog fix | -61 to -70 | 5 of 5 | 34.50-60.76 | 0 |

Without acknowledgements one alert was lost at the weak link. With them every message arrived, including after the broker outages, where delays over 25 s are expected. The watchdog restarts happened while the watch was reconnecting; running the network task at the idle task's priority stopped them.

## Status

The proof-of-concept wrist detector runs on the watch and logs test trials to SD. The MQTT alert path to the Pi works, with acknowledgements and resending. The 60 s post-fall check passed its 10 trials. The waist board with barometer is wired on a breadboard (ESP32, MPU6050, BMP280) and its sensors have been checked. With both devices worn, the fused model detected 20 of 20 falls and cut false alarms from 18 to 11 of 20 compared with the wrist alone on the same movements. The false-alarm rate is still far above target.
